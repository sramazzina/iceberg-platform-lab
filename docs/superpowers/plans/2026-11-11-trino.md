# Trino as an optional SQL engine — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the optional service `trino` (profile `trino`) with the Iceberg REST catalogs
`nessie`, `polaris` and `rest`, so that a JDBC client (DBeaver) shows the catalogs, namespaces
and tables in its navigator, and Trino reads and writes the same tables as Spark.

**Architecture:** The official image `trinodb/trino:484` runs with a bash entrypoint wrapper
(`trino/entrypoint.sh`). The wrapper writes the Trino configuration to `/tmp/trino-etc` for the
catalogs that are on (`LAB_CATALOGS` = `COMPOSE_PROFILES`), then starts the launcher. Catalog
files use `${ENV:NAME}` for secrets. `polaris-setup` creates a dedicated principal `trino_user`.

**Tech Stack:** Docker Compose, Trino 484 (Java 25), bash, POSIX sh (`polaris-setup`), the
bash test helpers in `tests/lib/`.

**Spec:** `docs/superpowers/specs/2026-11-11-trino-design.md` (issue #54).

## Deviations from the spec (found while writing the plan, 2026-11-11)

Each item below wins over the spec. Task 7 records them in `NOTES.md`.

1. **S3 file system property.** The Trino 484 documentation
   (<https://trino.io/docs/484/object-storage/file-system-s3.html>) names the property
   `fs.s3.enabled=true`, not `fs.native-s3.enabled`. The catalog files use `fs.s3.enabled`.
2. **Query memory limits.** Trino 484 defaults: `query.max-memory-per-node` = 30% of the heap,
   `memory.heap-headroom-per-node` = 30% of the heap
   (<https://trino.io/docs/484/admin/properties-resource-management.html>). These defaults
   already follow `TRINO_HEAP`. The entrypoint does not set them (spec 6.4 asked for a derived
   value; the default is the "fixed fraction", 30%). `query.max-memory` default (20GB) is
   higher than the node limit, so the per-node limit applies on a single node.
3. **Health check.** The image has `/usr/lib/trino/bin/health-check` (Dockerfile
   `HEALTHCHECK`). The Compose health check calls it. Task 1 reads the script and confirms
   that it checks `/v1/info`.
4. **Profile `trino` in the Spark entrypoint.** `spark/entrypoint.sh` prints
   `no Spark catalog for profile 'trino'` when `trino` is in `COMPOSE_PROFILES`. Task 3 makes
   it skip `trino` like `thrift` (the spec did not list this change).
5. **Test secrets path.** `tests/trino-config.sh` cannot mount a dummy file on
   `/run/lab-secrets` (the service already mounts it). The entrypoint reads the path from
   `LAB_TRINO_SECRETS` (default `/run/lab-secrets/trino_user.env`).
6. **shellcheck.** `tests/lint.sh` runs `bash -n`, not `shellcheck`, and `shellcheck` is not
   installed on the EC2 VM. `bash -n` covers `trino/entrypoint.sh` with no change.
   `tests/check-no-secrets.sh` already scans every tracked file, `trino/` included.
7. **`NOTES.md` on `main`.** User rule (2026-11-11): `NOTES.md` is committed directly to
   `main`. Task 7 does it after the PR is open, not on `feat/trino`.

```sh
# ensure_principal NAME FILE PREFIX SERVICE: creates the principal NAME and writes its
# credentials to FILE as PREFIX_CLIENT_ID and PREFIX_CLIENT_SECRET. Polaris shows a secret only
# once: in the answer to the create call, or to a reset call. When NAME exists, FILE is kept
# if a token call with it works; else the credentials are reset and FILE is written again.
# SERVICE is the Compose service that reads FILE.
ensure_principal() {
  name=$1; out=$2; prefix=$3; service=$4
  code=$(call POST /principals "{\"principal\":{\"name\":\"$name\"}}")
  case $code in
    201) echo "polaris-setup: principal $name created"; write=1 ;;
    409)
      # The file is kept only if it works: a token call as NAME (nothing is printed).
      if [ -s "$out" ] && ( . "$out" && eval "id=\${${prefix}_CLIENT_ID:-}; secret=\${${prefix}_CLIENT_SECRET:-}" \
          && curl -fsS -o /dev/null -X POST "$API/api/catalog/v1/oauth/tokens" \
            --user "$id:$secret" -d grant_type=client_credentials -d scope=PRINCIPAL_ROLE:ALL ) >/dev/null 2>&1; then
        echo "polaris-setup: principal $name already present, credentials file kept"; write=0
      else
        reason="credentials file of $name does not work, credentials reset"
        [ -s "$out" ] || reason="principal $name already present, credentials reset"
        code=$(call POST "/principals/$name/reset" '{}')
        [ "$code" = 200 ] || fail "reset $name: HTTP $code"
        echo "polaris-setup: $reason"; write=1
      fi ;;
    *) fail "principal $name: HTTP $code: $(cat "$ANSWER")" ;;
  esac
  if [ "$write" = 1 ]; then
    id=$(field clientId)
    secret=$(field clientSecret)
    [ -n "$id" ] && [ -n "$secret" ] || fail "no clientId or clientSecret in the answer for $name"
    ( umask 077; printf '%s_CLIENT_ID=%s\n%s_CLIENT_SECRET=%s\n' "$prefix" "$id" "$prefix" "$secret" >"$out.new" )
    mv "$out.new" "$out"
    echo "polaris-setup: credentials written to secrets/${out##*/} (secrets/rustfs/ on the RustFS variant)"
    if [ "$code" = 200 ]; then
      echo "polaris-setup: credentials reset; run 'docker compose restart $service' if $service is already running"
    fi
  fi
}

ensure_principal spark_user /secrets/spark_user.env POLARIS_SPARK spark
# Created always, also when the profile trino is off: setup does not need to know the engines.
ensure_principal trino_user /secrets/trino_user.env POLARIS_TRINO trino
```

```bash
#!/usr/bin/env bash
# Writes the Trino configuration for the catalogs that are on (LAB_CATALOGS, a copy of
# COMPOSE_PROFILES) to /tmp/trino-etc, then starts Trino (single node). When arguments are
# given, runs them instead (tests/trino-config.sh). /etc/trino belongs to the image user
# trino; the container runs with LAB_UID, so the configuration goes to /tmp.
# The files hold no secret: the catalog files read them with ${ENV:NAME}.
set -euo pipefail

src=/lab
etc=/tmp/trino-etc
data=/tmp/trino-data
secrets=${LAB_TRINO_SECRETS:-/run/lab-secrets/trino_user.env}

IFS=', ' read -ra list <<<"${LAB_CATALOGS:-}"

rm -rf "$etc"
mkdir -p "$etc/catalog" "$data"

for profile in "${list[@]}"; do
  case $profile in
    # Profiles of services, not catalogs.
    thrift | trino) continue ;;
    '*')
      echo "trino-entrypoint: COMPOSE_PROFILES='*' is not supported for Trino; list the catalogs" >&2
      continue ;;
    # The profile baseline starts the rest fixture: Spark and Trino name the catalog rest.
    baseline) catalog=rest ;;
    *) catalog=$profile ;;
  esac
  if [[ ! -f $src/catalog/$catalog.properties ]]; then
    echo "trino-entrypoint: no Trino catalog for profile '$profile' (trino/catalog/$catalog.properties)" >&2
    continue
  fi
  if [[ $catalog == polaris ]]; then
    if [[ ! -f $secrets ]]; then
      echo "trino-entrypoint: polaris is selected but secrets/trino_user.env (secrets/rustfs/ on the RustFS variant) is missing: run make up (polaris-setup writes it)" >&2
      exit 1
    fi
    # Exported for ${ENV:...} in polaris.properties; never written to a file.
    set -a
    # shellcheck source=/dev/null
    source "$secrets"
    set +a
  fi
  cp "$src/catalog/$catalog.properties" "$etc/catalog/$catalog.properties"
  # S3-compatible storage: Trino rejects an empty s3.endpoint, so the lines are a fragment.
  if [[ -n ${S3_ENDPOINT:-} ]]; then
    cat "$src/catalog-s3-endpoint/$catalog.properties" >>"$etc/catalog/$catalog.properties"
  fi
done

# JVM options of the image default (core/docker/default/etc/jvm.config), with a fixed heap
# instead of -XX:MaxRAMPercentage, so that the heap does not follow the container limit.
cat >"$etc/jvm.config" <<EOF
-server
-agentpath:/usr/lib/trino/bin/libjvmkill.so
-Xmx${TRINO_HEAP:-2g}
-XX:G1HeapRegionSize=32M
-XX:+ExplicitGCInvokesConcurrent
-XX:+HeapDumpOnOutOfMemoryError
-XX:+ExitOnOutOfMemoryError
-XX:-OmitStackTraceInFastThrow
-XX:ReservedCodeCacheSize=256M
-XX:PerMethodRecompilationCutoff=10000
-XX:PerBytecodeRecompilationCutoff=10000
-Djdk.attach.allowAttachSelf=true
-Djdk.nio.maxCachedBufferSize=2000000
EOF

# Single node: coordinator and worker in one process. The query memory limits keep the
# Trino defaults (30% of the heap per node, 30% headroom), so they follow TRINO_HEAP.
cat >"$etc/config.properties" <<'EOF'
coordinator=true
node-scheduler.include-coordinator=true
http-server.http.port=8080
discovery.uri=http://localhost:8080
catalog.management=static
EOF

cat >"$etc/node.properties" <<EOF
node.environment=lab
node.data-dir=$data
node.id=\${ENV:HOSTNAME}
EOF

if (($# > 0)); then
  exec "$@"
fi

exec /usr/lib/trino/bin/launcher run --etc-dir "$etc"
```

````markdown
## Trino

Trino is an optional SQL engine on the same Iceberg catalogs as Spark. It reads and writes
the same tables: a table that Spark writes is visible in Trino at once, and the reverse.

1. Add `trino` to `COMPOSE_PROFILES` in `.env`, for example `nessie,trino`.
2. Run `make up`. Trino starts after the catalogs. Trino loads the catalogs at startup:
   after a change of `COMPOSE_PROFILES`, run `make up` again.
3. Run `make sql-trino`, then `SHOW CATALOGS;`.

[Memory per service](#memory-per-service)).

### Connect DBeaver to Trino

1. On a remote VM, open the tunnel for port 8080 (see [SSH tunnel](#ssh-tunnel)):
   `-L 8080:127.0.0.1:8080`.
2. In DBeaver, create a connection of type **Trino** (DBeaver downloads the driver).
3. Set the JDBC URL to `jdbc:trino://localhost:8080`. Set any user name. Leave the password
   empty.
4. Open the navigator. It shows the catalogs that are on (`nessie`, `polaris`, `rest`), their
   namespaces and their tables.

| Service | Limit | Set by |
|---|---|---|
| `spark` (JupyterLab, `spark-sql`, the ELT jobs) | no container limit; driver heap 4 GB | `spark/conf/spark-defaults.conf` |
| `spark-thrift` (profile `thrift`) | no container limit; driver heap 4 GB | `spark/conf/spark-defaults.conf` |
| `trino` (profile `trino`) | 3 GB container, 2 GB heap | `TRINO_MEM_LIMIT`, `TRINO_HEAP` in `.env` |
| `nessie` | 1 GB | `docker-compose.yml` |
| `polaris` | 1 GB | `docker-compose.yml` |
| `rest-fixture` | 512 MB | `docker-compose.yml` |
````
